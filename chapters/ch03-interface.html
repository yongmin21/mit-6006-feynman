PART II · 자료를 담는 방식

Chapter 3. 자료구조를 고르기 전에 연산부터 정의하라

자료구조는 상자가 아니라, 필요한 연산과 그 비용을 약속하는 구현이다.

학습목표

  • 문제의 요구를 Sequence 또는 Set 연산으로 번역한다.
  • 인터페이스와 구현을 분리하고 연산별 비용으로 구현을 선택한다.
  • 문제의 불변식과 워크로드를 먼저 적는다.

오늘의 문제

음악 재생 목록에는 “세 번째 곡 재생”과 “다음 곡 삽입”이 필요하다. 연락처에는 “이름이 민수인 사람 찾기”가 필요하다. 둘 다 데이터를 저장하지만 같은 자료구조를 고르면 될까?

Brute force · 일단 한 리스트에 담기

items = []

def find_key(key):
    for item in items:
        if item.key == key:
            return item
    return None

정확하지만 키 검색은 Θ(n)이다. 순서가 중요한지, 키가 중요한지 정의하지 않은 채 구현부터 골랐기 때문이다.

병목

병목은 “리스트가 느리다”가 아니다. 연락처의 주 연산인 find(key)가 매번 모든 항목을 읽는다는 점이다. 반대로 위치 접근이 핵심인 재생 목록에는 리스트가 자연스럽다.

아이디어 재발명

  1. 명사 대신 동사를 적는다: 가져오기, 넣기, 지우기, 찾기.
  2. 연산의 기준이 위치면 Sequence, 고유 키면 Set으로 묶는다.
  3. 가장 자주 쓰거나 반드시 빨라야 하는 연산에 맞춰 구현을 고른다.

MIT formalization

인터페이스대표 연산질문
Sequenceget_at(i), set_at(i,x), insert_at(i,x), delete_at(i)몇 번째 원소인가?
Setfind(k), insert(x), delete(k), find_min()키 k를 가진 원소인가?

인터페이스는 무엇을 할 수 있는지, 자료구조는 그 연산을 어떻게 구현하는지 말한다.

WHY?

같은 인터페이스를 만족하는 배열, 연결 리스트, 해시 테이블, 트리는 비용표가 다르다. 연산을 먼저 정의해야 “빠르다”를 문제에 맞게 말할 수 있다.

INVARIANT

Sequence에서는 원소의 상대적 순서가 의미를 유지한다. Set에서는 각 원소가 검색 가능한 키를 가지며, 키의 동일성 규칙이 모든 연산에서 일관되어야 한다.

TRADE-OFF

모든 연산을 동시에 Θ(1)로 만들 수는 없다. 위치 접근, 가운데 삽입, 키 검색 중 워크로드에 중요한 것을 우선한다.

DON’T USE THIS WHEN

구현 이름만 보고 선택하지 말자. “데이터가 많으니 해시 테이블” 같은 판단은 순서 탐색이나 최소 키 연산이 필요할 때 요구를 놓친다.

손으로 추적하기

Sequence [A,B,C]에 insert_at(1,X)를 적용하면 [A,X,B,C]다. Set {7:A,2:B}에 find(2)를 적용하면 위치가 아니라 키 2의 항목 B를 돌려준다. 같은 “찾기”라도 계약이 다르다.

의사코드

required = [get_at, insert_at, find]
priority = {get_at: high, insert_at: low, find: high}

for candidate in [array, linked_list, hash_table, tree]:
    reject candidate if it cannot provide every required operation
choose the remaining candidate with the best priority-weighted costs

Correctness · 계약을 지키는가

구현의 정확성은 내부 모양이 아니라 연산의 사후조건으로 증명한다. 예를 들어 insert_at(i,x) 뒤에는 길이가 하나 늘고, i의 값이 x이며, 기존 앞·뒤 원소의 상대 순서가 보존되어야 한다.

Complexity

인터페이스 자체에는 시간복잡도가 없다. 배열로 구현한 Sequence는 위치 접근이 Θ(1)이지만, 연결 리스트는 일반적으로 Θ(n)이다. 비용은 반드시 연산 + 구현 쌍으로 말한다.

MIT-style 문제

Mechanics

사진 앱의 “최근 사진 10개”, “ID로 사진 찾기”를 각각 Sequence/Set 연산으로 쓰라.

Recognition

앞뒤 삽입이 많고 임의 위치 접근은 없는 작업 큐에 중요한 연산을 고르라.

Invention

학생을 학번으로 찾으면서 성적 순서로도 순회해야 한다. 필요한 인터페이스와 보조 구조를 제안하라.

해설 보기
  1. 최근 순서의 get_at/순회, ID 기준 find.
  2. insert_first/last, delete_first가 핵심이며 get_at은 우선순위가 낮다.
  3. 학번 Set과 성적 순서를 유지하는 ordered 구조를 함께 두고, 갱신 시 두 구조가 같은 학생 집합을 담는 불변식을 유지한다.

Feynman Test

“배열과 Sequence가 같은 말이 아닌 이유”를 코드 없이 설명하라.

어떤 자료구조가 빠르다는 주장에 반드시 따라야 하는 질문은 무엇인가?

빈 종이 테스트

요구 → 연산 → 인터페이스 → 구현 → 비용 다섯 칸을 그리고 연락처 앱을 채워 보라.

한 장 요약

  • Sequence는 위치, Set은 키로 질문한다.
  • 인터페이스는 계약이고 자료구조는 구현이다.
  • 먼저 필요한 연산과 빈도를 적고, 나중에 구현을 고른다.

다음 장 연결

위치 접근이 가장 중요한 Sequence라면 어떻게 Θ(1)을 얻을까? 다음 장에서 연속 메모리와 주소 계산으로 배열을 재발명한다.
